# 2026-10-27

## Fixed: Roles not showing in admin panel (Settings > Roles)

- **Symptom:** Roles list empty; IDE reported `PHP0413 Use of unknown class App\Modules\Settings\Http\Resources\RoleRow` at RoleController.php:32.
- **Root cause:** `app/Modules/Settings/Http/Resources/RoleRow.php` was a copy-paste duplicate of `UserRow.php` — file declared `class UserRow`. So `RoleRow` never existed; `TableQuery::json(..., RoleRow::class)` threw `Class "..." not found` → `/settings/roles/data` returned HTTP 500 → table rendered empty.
- **Fix:** Rewrote RoleRow.php as a proper `RoleRow` JsonResource returning the keys `Settings/Roles/Index.vue` expects: `id`, `name`, `users` (users_count), `permissions` (permissions_count), `system` (name === 'super-admin'), `type` ('Full access' | 'Custom').
- **Verified:** class_exists true; endpoint returns HTTP 200 with all 4 roles (manager, Stock User, super-admin, viewer).
- **Audit side-notes (no change made):** only 1 filename/class mismatch in whole `app/`; no missing `App\*` class references remain; routes + permissions fine (`Gate::before` in CoreServiceProvider grants super-admin everything, so its 0 explicit permissions is expected).

## Added: delete from the Roles list (was only available inside the form)

- **Complaint:** no delete option on the Roles list; delete only existed on `Settings/Roles/Form.vue` and only when the role had 0 users. Other doctype lists (e.g. `Pages/Examples/List.vue`, `Pages/Settings/Users/Index.vue`) delete from the list via `#bulk` + `ConfirmDialog`.
- **Backend:** `RoleController@bulkDestroy` — validates `ids[]` (array, max 500, integers), deletes roles that are neither `super-admin` nor assigned to users, logs `role.deleted` per role, returns a `success` flash with deleted/skipped counts. Route: `POST settings/roles/bulk-delete` behind `can:settings.roles.delete` (registered in `app/Modules/Settings/routes.php`).
- **Frontend:** `Pages/Settings/Roles/Index.vue` — `:selectable="canDelete"`, `#bulk` slot with a danger Delete button, per-row trash `#row-end` action (only for deletable rows, `@click.stop` so it doesn't trigger row navigation), `ConfirmDialog` showing deletable vs skipped counts and disabled when nothing is deletable.
- **Rules kept:** `super-admin` never deletable; roles with assigned users must be unassigned first. Both are surfaced in the confirm dialog rather than silently failing.
- **Verified:** functional test with a disposable role — 1 deleted, super-admin + manager (1 user) skipped, role count returned to 4, temp role removed. `npm run build` passes.

## Data-state issue found, NOT fixed (needs user decision)

- `manager` and `viewer` roles have **0 permissions** in DB. `PermissionSeeder` only calls `syncPermissions()` when `$role->wasRecentlyCreated` is true, so roles that already existed at seed time never received their default permission sets. Re-running the seeder will NOT repair them (they already exist) — they must be re-synced explicitly or re-granted from the Roles screen.
- **Update 13:19:** user deleted `viewer`, `manager`, `Stock User` via the new bulk-delete UI and disabled `khan@gmail.com`. DB now has 1 role (super-admin), 2 users. This is user action, not a bug.

## Full audit written → `AUDIT.md` (repo root)

Read all of `app/Core`, `app/Modules`, `routes/`, `resources/js/core`, config, migrations; reproduced findings with tinker + throwaway feature tests (all probe files deleted afterwards).

**P0 (all proven):**
1. `bootstrap/app.php:23` type-hints `Response` without importing it → **every** 403/404/ValidationException throws `TypeError` → 500. `Pages/Errors/Error.vue` is unreachable. `php artisan test` fails on this line. Fix = `use Symfony\Component\HttpFoundation\Response;`
2. `AttachmentController` IDOR — a 0-permission user listed, downloaded (200) and deleted (204) another user's attachment. `authorizeType()` only checks the type permission; `demo` has `can => null`.
3. `RoleController@update` privilege escalation — role with only `settings.roles.update` granted itself all 10 permissions.
4. `UserController@update` self role-assignment — user with only `settings.users.update` gave self a 10-permission role.
5. `composer setup` never runs `db:seed`, so `admin:create` crashes (`RoleDoesNotExist`) on a clean install.

**P1:** partial PUT without `is_active` silently disables the account (proven); `is_active` not in `#[Fillable]` + `EnsureUserActive` null-check → `Auth::login(User::create())` immediately logs out (proven); login throttle keyed on email+ip is bypassed by rotating emails (8/8 unthrottled); attachment upload never validates the parent record / no quota / no cleanup; no password reset, email verification or 2FA; no security headers.

**UI:** 0 responsive breakpoints in the entire codebase (grep for `sm:|md:|lg:` → 0); `.btn`/`.nav-btn` have no `:focus-visible` ring; select-all only covers loaded rows; no unsaved-changes guard; no Inertia progress bar; README still Laravel default.

**Ruled out (checked, not vulnerable):** `storage/{path}` route from `'serve' => true` — unsigned access 403, `?upload=1` disables rather than enables the bypass. `composer audit` / `npm audit` clean. No raw SQL, no `v-html`.
